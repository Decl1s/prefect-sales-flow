# Лабораторная: меняй вход, смотри результат, затем меняй код

Начальная подготовка: задача 01 в VS Code либо `.venv/bin/python scripts/workshop.py prepare`.
Команды ниже выполняются из корня проекта. В Windows используй
`.venv/Scripts/python.exe`. Для нового чистого набора:
`scripts/workshop.py prepare --folder workspace/learn-2`; при запуске приложения
тогда тоже указывай пути learn-2. Скрипт никогда не сбрасывает уже созданные правки.

Уровни 1–6 меняют только учебный вход или способ запуска. Уровни 7–10 меняют код:
сначала предскажи результат, затем запускай и объясняй расхождение. Результаты
preview находятся только в памяти; Prefect сохраняет файлы штатной командой run.

## 1. Увидеть все промежуточные данные — 5 минут

Открой `workspace/learn/input/baseline.csv`, затем выполни:

```bash
.venv/bin/python scripts/workshop.py preview --case baseline
```

Найди stage_2_quality: input_rows=8, unique_orders=6, duplicates=2.
В stage_3_summary ожидаются paid_orders=5, cancelled_orders=1, revenue_cents=159000.
Дни: 36000 и 123000, количество единиц: 5 и 7.
Поставь точку F9 в aggregate на строке сложения выручки и выбери отладку без Prefect.
Объясни, почему входных строк восемь, оплаченных заказов пять, а товаров двенадцать.

Проверка понимания: заказ может содержать несколько товаров; точные дубли не считаются
новыми заказами, cancelled не даёт выручку. Нельзя заменить одно из этих чисел другим.

## 2. Точный дубль и ключ пакета — 5 минут

```bash
.venv/bin/python scripts/workshop.py preview --case extra-duplicate
```

В этой копии добавлена ещё одна O0002. Ожидается input_rows=9, duplicates=3,
unique_orders=6 и прежние 159000. Сравни run_key с baseline: он другой.
Проверь код read_source и объясни, что именно хэшируется.

Дополнительный опыт: скопируй baseline.csv под новым именем, ничего не меняя в байтах.
Для запуска нового имени используй штатный `run --input ...`. Одинаковые байты
с той же VERSION дадут одинаковый ключ, имя файла в формулу не входит.

Почему так: дедупликация заказов — правило данных; идентификация пакета — другое
правило. В текущей версии пакет определяется байтами, даже если суммы совпали.

## 3. Конфликт нельзя исправить повтором — 5 минут

```bash
.venv/bin/python scripts/workshop.py preview --case conflict
```

Ожидается DataError и код выхода 1. В последней O0001 количество равно 3, тогда как
в первой равно 2. Открой quality_gate и сравнение unique[key] с record.
Исправь количество в последней строке на 2 и повтори preview.
Теперь ожидаются 9 строк, 3 дубля, 159000 копеек.

Объясни, почему «выбрать последнюю строку» опасно: расположение в CSV не доказывает,
что запись новее. Для разрешения обновлений нужно поле версии/времени и отдельная
политика, а не добавление retries к quality_task.

## 4. Отмена заказа — 5 минут

```bash
.venv/bin/python scripts/workshop.py preview --case cancelled
```

В обеих копиях O0005 выставлен cancelled. Ожидается выручка 59000, оплаченных 4,
отменённых 2. За 2 октября останется 23000, 2 оплаченных заказа и 5 единиц товара.
За 1 октября остаётся 36000. Найди continue в aggregate и проследи, что оно пропускает.

Самостоятельно отмени O0001 в baseline, изменив обе его копии. Доход должен стать
129000, за 1 октября — 6000. Если исправишь только одну копию, возникнет конфликт:
ты описал две разные версии одного заказа. После опыта верни две строки Undo либо
создай новую лабораторную папку. Остальные задания предполагают исходный baseline.

## 5. Настоящий retry и повтор загрузки — 5 минут

Выполни задачи 03, 04 и 05 либо:

```bash
.venv/bin/python -m sales_flow run --input workspace/learn/input/baseline.csv --output workspace/learn/output --prefect-home workspace/learn/prefect --fail-once
.venv/bin/python scripts/workshop.py inspect --case baseline
.venv/bin/python -m sales_flow run --input workspace/learn/input/baseline.csv --output workspace/learn/output --prefect-home workspace/learn/prefect --fail-once
```

В чистой выходной папке первый запуск: reused=false, publish_attempts=2. Второй:
reused=true, publish_attempts=1. Если оба показывают reused=true, результат уже был
получен раньше. Для нового опыта задай другую --output, например workspace/learn/retry-2;
команда inspect читает стандартную папку output, поэтому результат retry-2 открой в Explorer.

В publish найди проверку target перед `if fail`. Объясни, почему сохранённый корректный
результат не нужно искусственно ломать для демонстрации отказа.
В orchestration.py посмотри retries=2: это максимум 3 попытки, но наш отказ случается
только один раз. Число дополнительных попыток и фактическое число исполнений различаются.

## 6. Повреждение результата — 5 минут

Для этого опыта сохрани baseline в отдельный выход, чтобы оставить результат задания 5:

```bash
.venv/bin/python -m sales_flow run --input workspace/learn/input/baseline.csv --output workspace/learn/corrupt-output --prefect-home workspace/learn/prefect
```

В Explorer открой единственную подпапку corrupt-output и добавь слово в report.md.
Повтори ту же команду. Ожидается PublishError, код выхода 1, изменённый файл остаётся
с твоими байтами. Приёмник не должен молча стереть файл, происхождение которого непонятно.
Верни правку через Undo или используй новый --output для следующего опыта.

В scripts/smoke.py найди observed_retry: эта проверка доказывает, что повреждение
не повторяется. Ответь, почему нельзя лечить его увеличением retry_delay_seconds.

Повтори preview для new-product.

В отдельной проверке неизвестный товар вроде another всё ещё должен отклоняться.
Запусти задачу 07. Исходные 19 тестов должны сохранить успех, новый тест тоже должен пройти.

Почему меняем VERSION: поле product стало принимать новый смысловой набор значений.
Почему не редактируем uv.lock: новый элемент множества не требует новой библиотеки.

## 8. Сводка по товарам — 15–20 минут

Задача: добавить в итог `by_product`, сохранив существующий daily. Меняй aggregate,
не quality_gate и не retry. Список отсортируй по product для стабильного вывода.
Для исходного baseline ожидается:

| product | orders | units | revenue_cents |
| --- | --- | --- | --- |
| bag | 1 | 2 | 100000 |
| book | 2 | 3 | 45000 |
| pen | 2 | 7 | 14000 |

Общий доход трёх строк — 159000. Отменённая bag не должна попасть в таблицу.
Добавь проверку полного списка в test_core.py и подними VERSION до следующей
неиспользованной версии. Если нужно показать новую таблицу человеку, отдельно дополни artifacts.

Почему два места изменения: aggregate отвечает за смысл, artifacts — за представление.
Сначала можно получить правильный JSON, затем независимо оформить отчёт.

## 9. Максимальный заказ — 10–15 минут

Добавь в aggregate поля max_order_id и max_order_revenue_cents для оплаченных заказов.
Для baseline ожидается O0005 и 100000. Если все заказы отменены, выбери и опиши
контракт: например, null для ID и 0 для суммы. При равных суммах заранее определи
правило, например меньший order_id, чтобы порядок входа не менял ответ.

Проверь три случая: обычный baseline, все cancelled, две равные максимальные суммы
в разном порядке. Новая VERSION обязательна. Не используй самый большой unit_price_cents:
заказ из двух дешёвых товаров может быть дороже одного дорогого.

## 10. Подготовить своё поле скидки — 20–30 минут

Сначала запиши договорённость: новое поле discount_cents — скидка на весь заказ,
целое от 0 до quantity × unit_price_cents. Она не умножается на количество второй раз.
Затем по карте START_HERE найди изменения: HEADER, разбор полей и проверка границ
в quality_gate; преобразование в int; формула в aggregate; строки генератора и
лабораторной; тесты и документация; новая VERSION.

Пример проверки: две книги по 15000 со скидкой 3000 дают 27000, а не 24000.
Скидка 30001 при сумме 30000 должна отклоняться. Для исходного набора с нулевыми
скидками доход остаётся 159000. Точные дубли и конфликты продолжают учитывать все поля.
Старый CSV без колонки нужно либо явно отклонять, либо поддержать версионным адаптером:
не подставляй молча нули без решения о совместимости.

Это упражнение намеренно требует обновления старых fixtures: изменился сам контракт,
поэтому тесты со старым заголовком должны быть пересмотрены осмысленно. Не удаляй
проверки плохих данных ради зелёного результата.
